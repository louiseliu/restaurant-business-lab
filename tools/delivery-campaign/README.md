# 外卖活动到底多赚了多少｜经营决策样板

**状态：可离线使用的条件测算器；所有初始值为演示数据，不是真实门店经营结果。**

## 直接使用

1. 下载 `index.html`，用现代浏览器打开。只需这一份文件，不需要安装软件、联网、登录或上传数据。手机需要用支持运行本地 HTML/JavaScript 的浏览器打开；文件预览器未必支持。
2. 先读页面顶部的三项限制，再替换 N、α、cₚ、cᵦ、F。
3. 看当前条件增量贡献，再看 0%–100% 的情景图与持平点。**不知道 α 就保留多种假设，不要默认全部是新增。**
4. 不知道单均贡献时，展开结算辅助表，分别填写活动单与被替代的原价单；点击应用才会覆盖上方两项。成本已从结算扣除的，对应项填 0。
5. 点“下载当前测算记录”保存本地 JSON；点“打印 / 存为 PDF”调用浏览器打印。**刷新会恢复演示，页面不自动保存。** JSON 是留痕文件，本版本不提供导入。

嵌入其他页面时，下载与打印按钮自动隐藏，避免受限 iframe 的无效动作。先从外层下载独立 HTML，再本地使用这些功能。

## 五个数怎么取

| 输入 | 含义与来源 | 最容易犯的错 |
|---|---|---|
| N，单 | 同一门店、活动期间内的平台/内部活动归因订单；按统一完成、取消、退款规则匹配结算和成本 | 把归因当增量；多活动重复计单 |
| α，0%–100% | N 中无活动就不会发生、并非从其他订单转移而来的比例；没有可靠识别时只作情景 | 用新客、核销或平台归因率直接替代因果增量率 |
| cₚ，元/单 | 活动订单总同口径结算减尚未扣除的变动成本，再除以匹配订单数 | 用成交额代替商户结算；已扣佣金/配送/优惠又扣一遍 |
| cᵦ，元/单 | 被替代的同类原价订单，在无活动时本可贡献的钱 | 随意拿全店平均、标价或另一菜品组合当基线 |
| F，元 | 仅因活动新增、且未计入单均贡献的固定支出 | 重复扣活动费；把不变房租再算成增量损失 |

按同一币种、含税/不含税、退款观察窗、活动归因规则取数。原价单也需按真实结算与成本取贡献，不是按菜品标价。结算明细有成本代扣时，保留“已扣 / 未扣”的逐项映射。

## 演示如何读

演示输入：N=1,000 单、cₚ=8 元、cᵦ=12 元、F=2,000 元。

| 假设 α | 条件增量贡献 |
|---:|---:|
| 0% | −6,000 元 |
| 25% | −3,000 元 |
| 40%（默认） | −1,200 元 |
| 50% | 0 元 |
| 75% | +3,000 元 |
| 100% | +6,000 元 |

所以在这组**演示条件**下，需约 50% 的归因订单是真增量才持平。默认活动单产生 8,000 元贡献，但替代掉了 7,200 元原价单贡献，再扣 2,000 元活动固定增量支出，得到 −1,200 元。不能把它说成任何门店实际亏了 1,200 元。

## 模型与适用边界

`Δ = N × [cₚ − (1 − α) × cᵦ] − F`

这是“做活动”与“不做活动”的**简化反事实贡献差**。无活动基线中，(1−α)N 个订单仍会以同类原价订单存在，αN 个订单不会发生。相同的日常固定费用在两边抵消。

只有 N>0 且 cᵦ>0 时，最低持平增量比例为：

`α* = 1 − cₚ/cᵦ + F/(N×cᵦ)`

- α*<0：0%–100% 都为正；α*=0：0% 持平。
- 0<α*<1：低于它为负，等于它持平，高于它为正。
- α*=1：只有 100% 才持平；α*>1：有效范围内无法持平，不裁剪成 100%。
- N=0：结果为 −F，不算比例阈值。
- cᵦ=0：结果与 α 无关；cᵦ<0：斜率反转，不给“至少需要”的标准阈值。
- cₚ、cᵦ可为负数。N 必须是非负整数；F 不得为负；所有输入必须是有限数且不为空。

**不能省略的条件：**非增量活动单只替代同类原价订单；没有额外跨渠道、跨时段、跨店产能挤占；输入对应同一范围；其余参数在敏感性图中保持不变。订单结构差异、阶梯加班、退款未结清、跨期复购与品牌影响等，需要分组或扩展模型。这里不是全店净利润、因果实测、长期收益，也不是加盟投资回报。

### 数值约束

技术上限用于拒绝单位错误和过大输入，不是经营可行性标准：N≤10,000,000；|cₚ|、|cᵦ|≤1,000,000 元；0≤F≤10,000,000,000 元。辅助表各项为 0–1,000,000 元。极小正 cᵦ 导致比例阈值溢出时，明确显示“数值精度限制”，不输出无穷大或伪阈值。

采用 JavaScript Number 浮点计算，金额显示到分，比例显示最多两位小数；不先四舍五入阈值再分类。近零结果显示“约为持平”。分数量的增量/替代订单是情景期望数，不冒充观测整单。敏感性图是条件情景，不是置信区间、预测区间或概率分布。

## 取数清单与验证

### 内部取数表

- 订单：门店、订单标识、时段、菜品、渠道、活动标记、取消/退款状态；订单标识不需要输入此工具。
- 结算：顾客实付、平台真实承担补贴、商家折扣、佣金、配送、其他代扣、退款与到账；逐项对到最终商户结算。
- 成本：食材、包装、增量人工、其他变动成本、活动固定增量支出；写明期间和已计入口径。
- 可比基线：被替代原价订单的菜品、渠道、时段与客群，基线成本和结算为何可比。
- 护栏：全店各渠道订单和贡献、等待/出餐、取消退款、缺货、跨日消费，检查转移与挤占。
- 证据记录：每个输入填来源、期间、口径、已知误差；α 同时注明“实验估计 / 其他识别 / 纯假设”。

### 最小验证办法

1. 先核对结算与成本，抽样逐单走通“订单→结算→成本→贡献”，再与总账汇总对齐。
2. 仅在已有经营授权下设计随机活动/保留组，预先定义范围、观察窗、总订单/总贡献指标与护栏；控制跨组、商圈溢出和产能串扰。
3. 比较同范围的总结果而非活动标签。只有新增量属于 N 覆盖范围、对照可比时，才可据此估计 α。否则应重建模型范围。
4. 报告样本量、统计不确定性、未成熟退款与异常；增量估计落在 0%–100% 外不能静默截断。
5. 没有可信识别时，坚持多情景；不能用历史同期简单差、前后差或自选参与店与未参与店差当作活动因果效果。

本包只准备工具和方案，没有开展真实活动、触达外部人员、取得私人经营数据或修改真实系统。

## 源码、复算与验收

```sh
python3 build.py
node tests/test-model.cjs
```

不需要安装依赖。`model.js` 是纯计算；`ui.js` 是浏览器交互；`index.template.html` 是版式/说明；`build.py` 将两份 JS 内联，生成可独立打开的 `index.html` 与本地预览副本 `dist/index.html`。测试逐字比对内嵌源码，避免“测的是另一套代码”。

测试结果：`tests/test-results.json`、`tests/test-console.txt`；实际浏览器验收记录：`tests/browser-qa.md`。数学边界由另一个代理独立复算，默认与 0/100% 等例一致；这不构成真实经营数据验证。
