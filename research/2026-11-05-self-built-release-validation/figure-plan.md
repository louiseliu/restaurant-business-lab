# 图示建议：AI自建系统发版验收

两图均标注“研究示意；非产品界面、事故统计或已执行测试”。不使用来源截图，不生成事故损失、通过率、效率或成本数字。正文完整保留，图示服务于经营取舍，不替代正文与证据边界。

## 图一：一次权限修复，要同时证明谁能用、谁不能用

目的：说明报障店长的单次确认不能覆盖多套身份，避免把拒绝匿名当成全部完成。

用清晰的矩阵展示“测试身份/实际权限约定/预期检查/由谁解释”。合成身份包括匿名者、合法门店A账号、合法总部账号、门店B账号尝试读取A店限定记录；对应预期分别为拒绝、允许本店范围、按已授权范围允许、拒绝跨店越权。必须注明“示例权限约定，需按本店真实系统替换；不意味着总部拥有所有权限”。

以两条汇合的线强调：不应访问的被拒绝、应当访问的能完成操作，两类证据共同支持权限验收。旁注“报障人：确认原问题”“跨入口负责人：确认其他合法使用及越权边界”。S2只支持鉴权缺半边的项目自述；具体矩阵及分工是作者建议。

## 图二：批准到运行，要沿同一个发布版本查到底

目的：区分测试、发布回执和实际运行，并解释为什么旧包可能覆盖已上线改动。

主线为“已运行版本与现有功能 → 本次源码与改动范围 → 最终构建及对应测试 → 实际入口的运行版本与关键流程”。在“最终构建”下设置检查点“包含此前应保留改动”，在“实际入口”下设置检查点“合法身份完成任务”。测试后又合入改动或换构建包，箭头返回“核对变化、重验受影响路径”。

下方单独放两张不可混同的案例卡：“S2鉴权缺口：没测正常门店身份”“S4产物缺口：旧源码包覆盖新入口”。卡片标“同一项目的两项自述，非同一事故”。旁注“S4防回退在固定版本中只告警，未强制拦截；上述完整验收线为本文建议”。

底部经营条件：证据完整、原有功能保留、恢复有人接手，才扩大同类自动放行；缺任何一项，先维持人工放行、缩小范围。自动修复例外只在来源说明中标“刚上线、真实首次触发仍观察”，不画成已成熟自动闭环。
